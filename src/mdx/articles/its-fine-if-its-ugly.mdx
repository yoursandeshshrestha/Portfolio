When I first started, I thought everything had to look clean from the start.
Well-structured code. Reusable components. Perfect naming.
But in real projects, that is not how things go.
Most of the time, the first version is messy. It is fast. It is a bit hard to look at. But it works. That is what matters.

You cannot improve something if it does not exist. You cannot clean up a feature that was never shipped.

I have learned that the first goal is always the same, get it working. Then improve it once it is real.

## Why it is fine

The first time you build something, you are learning how it works.  
You are testing ideas.  
You are seeing what is needed and what is not.

That is why it is fine if the code is not perfect.

It is better to:

- Ship something simple
- See what breaks
- Fix what matters

Instead of:

- Trying to guess everything
- Overengineering the unknown
- Taking a week for something no one uses

## What I do now

Now I build in steps.

Step one, make it work.  
Step two, test it with others.  
Step three, clean it up if it is staying.

If it never ships, none of the structure or polish matters.

## Just do not leave it forever

There is a difference between writing fast code and leaving messy code.

If something works and people depend on it, take time to improve it.  
Rename things.  
Move things around.  
Write comments for others.  
Make it easy for the next person, which might be you in a month.

But do not slow down your first version because you are afraid of doing it wrong.

## What helped me

The features I learned the most from were the ones I shipped early, fixed quickly, and rewrote better later.

It gave me real feedback.  
It helped the team move forward.  
And the second version was always better, because now I understood what I was building.

Build the version that works.  
Then clean it when it makes sense.

It is not lazy, it is practical. That is how things get built.
